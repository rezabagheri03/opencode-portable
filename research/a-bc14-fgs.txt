<p>To help developers be more intentional with defining user-facing <a href="/guide/components/foreground-services">foreground
services</a>, Android 10 introduced the <code translate="no" dir="ltr">android:foregroundServiceType</code>
attribute within the <a href="/guide/topics/manifest/service-element"><code translate="no" dir="ltr">&lt;service&gt;</code></a> element.</p>

<p>If your app targets Android 14, it must specify appropriate foreground service
types. As in previous versions of Android, multiple types can be combined. This
list shows the foreground service types to choose from:</p>

<ul>
<li><a href="/about/versions/14/changes/fgs-types-required#camera"><code translate="no" dir="ltr">camera</code></a></li>
<li><a href="/about/versions/14/changes/fgs-types-required#connected-device"><code translate="no" dir="ltr">connectedDevice</code></a></li>
<li><a href="/about/versions/14/changes/fgs-types-required#data-sync"><code translate="no" dir="ltr">dataSync</code></a></li>
<li><a href="/about/versions/14/changes/fgs-types-required#health"><code translate="no" dir="ltr">health</code></a></li>
<li><a href="/about/versions/14/changes/fgs-types-required#location"><code translate="no" dir="ltr">location</code></a></li>
<li><a href="/about/versions/14/changes/fgs-types-required#media"><code translate="no" dir="ltr">mediaPlayback</code></a></li>
<li><a href="/about/versions/14/changes/fgs-types-required#media-projection"><code translate="no" dir="ltr">mediaProjection</code></a></li>
<li><a href="/about/versions/14/changes/fgs-types-required#microphone"><code translate="no" dir="ltr">microphone</code></a></li>
<li><a href="/about/versions/14/changes/fgs-types-required#phone-call"><code translate="no" dir="ltr">phoneCall</code></a></li>
<li><a href="/about/versions/14/changes/fgs-types-required#remote-messaging"><code translate="no" dir="ltr">remoteMessaging</code></a></li>
<li><a href="/about/versions/14/changes/fgs-types-required#short-service"><code translate="no" dir="ltr">shortService</code></a></li>
<li><a href="/about/versions/14/changes/fgs-types-required#special-use"><code translate="no" dir="ltr">specialUse</code></a></li>
<li><a href="/about/versions/14/changes/fgs-types-required#system-exempted"><code translate="no" dir="ltr">systemExempted</code></a></li>
</ul>

<p>If a use case in your app isn&#39;t associated with any of these types, we strongly
recommend that you migrate your logic to use <a href="/topic/libraries/architecture/workmanager">WorkManager</a> or
<a href="/develop/background-work/background-tasks/uidt">user-initiated data transfer jobs</a>.</p>

<p>The <code translate="no" dir="ltr">health, remoteMessaging, shortService, specialUse</code>, and <code translate="no" dir="ltr">systemExempted</code>
types are new in Android 14.</p>

<p>The following code snippet provides an example of a foreground service type
declaration in the manifest:</p>
<div></div><devsite-code><pre class="devsite-click-to-copy" translate="no" dir="ltr" is-upgraded syntax="XML"><code translate="no" dir="ltr">&lt;manifest<span class="devsite-syntax-w"> </span>...&gt;
<span class="devsite-syntax-w">  </span>&lt;uses-permission<span class="devsite-syntax-w"> </span>android:name="android.permission.FOREGROUND_SERVICE"<span class="devsite-syntax-w"> </span>/&gt;
<span class="devsite-syntax-w">  </span>&lt;uses-permission<span class="devsite-syntax-w"> </span>android:name="android.permission.FOREGROUND_SERVICE_MEDIA_PLAYBACK"<span class="devsite-syntax-w"> </span>/&gt;
<span class="devsite-syntax-w">    </span>&lt;application<span class="devsite-syntax-w"> </span>...&gt;
<span class="devsite-syntax-w">      </span>&lt;service
<span class="devsite-syntax-w">          </span>android:name=".MyMediaPlaybackService"
<span class="devsite-syntax-w">          </span>android:foregroundServiceType="mediaPlayback"
<span class="devsite-syntax-w">          </span>android:exported="false"&gt;
<span class="devsite-syntax-w">      </span>&lt;/service&gt;
<span class="devsite-syntax-w">    </span>&lt;/application&gt;
&lt;/manifest&gt;
</code></pre></devsite-code>
<p>If an app that targets Android 14 doesn&#39;t define types for a given service in
the manifest, then the system will raise <code translate="no" dir="ltr">MissingForegroundServiceTypeException</code>
upon calling <a href="/reference/android/app/Service#startForeground(int,%20android.app.Notification)"><code translate="no" dir="ltr">startForeground()</code></a> for that service.</p>

<h2 id="permission-for-fgs-type" data-text="Declare new permission to use foreground service types" tabindex="-1">Declare new permission to use foreground service types</h2>


<p>If apps that target Android 14 use a foreground service, they must declare a
specific permission, based on the foreground service type, that Android 14
introduces. These permissions appear in the sections labeled &quot;permission that
you must declare in your manifest file&quot; in the <a href="#use-cases">intended use cases and
enforcement for each foreground service type</a> section on this page.</p>

<p>All of the permissions are defined as <a href="/guide/topics/permissions/overview#install-time">normal permissions</a> and are
granted by default. Users cannot revoke these permissions.</p>
<aside class="caution"><strong>Caution:</strong><span> If you call <a href="/reference/android/app/Service#startForeground(int,%20android.app.Notification)"><code translate="no" dir="ltr">startForeground()</code></a> without declaring the appropriate
foreground service type permission, the system throws a
<a href="/reference/java/lang/SecurityException"><code translate="no" dir="ltr">SecurityException</code></a>.</span></aside>

<h3 id="include-fgs-type-runtime" data-text="Include foreground service type at runtime" tabindex="-1">Include foreground service type at runtime</h3>


<p>The best practice for applications starting foreground services is to use the
<code translate="no" dir="ltr">ServiceCompat</code> version of <a href="/reference/androidx/core/app/ServiceCompat#startForeground(android.app.Service,int,android.app.Notification,int)"><code translate="no" dir="ltr">startForeground()</code></a> (available in androidx-core
1.12 and higher) where you pass in a bitwise
integer of foreground service types. You can choose to pass one or more type
values.</p>

<p>Usually, you should declare only the types required for a particular use case.
This makes it easier to meet the <a href="/guide/components/foreground-services#fgs-prerequisites">system&#39;s expectations for each foreground
service type</a>.
In cases where a foreground service is started with multiple types,
then the foreground service must adhere to the <a href="/guide/components/foreground-services#runtime-permissions">platform enforcement
requirements</a>
of <strong>all</strong> types.</p>
<div></div><devsite-code><pre class="devsite-click-to-copy" translate="no" dir="ltr" is-upgraded syntax="Kotlin"><code translate="no" dir="ltr"><span class="devsite-syntax-n">ServiceCompat</span><span class="devsite-syntax-p">.</span><span class="devsite-syntax-na">startForeground</span><span class="devsite-syntax-p">(</span><span class="devsite-syntax-m">0</span><span class="devsite-syntax-p">,</span><span class="devsite-syntax-w"> </span><span class="devsite-syntax-n">notification</span><span class="devsite-syntax-p">,</span><span class="devsite-syntax-w"> </span><span class="devsite-syntax-n">FOREGROUND_SERVICE_TYPE_LOCATION</span><span class="devsite-syntax-p">)</span>
</code></pre></devsite-code>
<p>If the foreground service type is not specified in the call, the type defaults
to the values defined in the manifest. If you didn&#39;t specify the service
type in the manifest, the system throws
<a href="/reference/android/app/MissingForegroundServiceTypeException"><code translate="no" dir="ltr">MissingForegroundServiceTypeException</code></a>.</p>

<p>If the foreground service needs new permissions after you launch it, you
should call <code translate="no" dir="ltr">startForeground()</code> again and add the new service types. For
example, suppose a fitness app runs a running-tracker service that always needs
<code translate="no" dir="ltr">location</code> information, but might or might not need <code translate="no" dir="ltr">media</code> permissions. You
would need to declare both <code translate="no" dir="ltr">location</code> and <code translate="no" dir="ltr">mediaPlayback</code> in the manifest. If a
user starts a run and just wants their location tracked, your app should call
<code translate="no" dir="ltr">startForeground()</code> and pass just the <code translate="no" dir="ltr">location</code> service type. Then, if the user
wants to start playing audio, call <code translate="no" dir="ltr">startForeground()</code> again and pass
<code translate="no" dir="ltr">location|mediaPlayback</code>.</p>

<p><a id="system-checks-appropriate-use-fgs"></a></p>

<h2 id="system-runtime-checks" data-text="System runtime checks" tabindex="-1">System runtime checks</h2>


<p>The system checks for proper use of foreground service types and confirms that
the app has requested the proper runtime permissions or uses the required APIs.
For instance, the system expects apps that use the foreground service type
<a href="/reference/android/content/pm/ServiceInfo#FOREGROUND_SERVICE_TYPE_LOCATION"><code translate="no" dir="ltr">FOREGROUND_SERVICE_TYPE_LOCATION</code></a> type to request either
<code translate="no" dir="ltr">ACCESS_COARSE_LOCATION</code> or <code translate="no" dir="ltr">ACCESS_FINE_LOCATION</code>.</p>

<p>This implies that apps must follow a very specific
order of operations when requesting permissions from the user and starting
foreground services. Permissions must be requested and granted <em>before</em> the
app attempts to call <code translate="no" dir="ltr">startForeground()</code>. Apps that request the appropriate
permissions after the foreground service has been started must change this order
of operations and request the permission before starting the foreground service.</p>
<aside class="caution"><strong>Caution:</strong><span> If your app doesn&#39;t fulfill all of the runtime requirements for
starting a foreground service, the system throws a <a href="/reference/java/lang/SecurityException"><code translate="no" dir="ltr">SecurityException</code></a>
after you call <code translate="no" dir="ltr">startForeground()</code> for that service. This prevents the
foreground service from starting, might cause a running foreground service to be
removed from the foreground process state, and might cause your app to crash.</span></aside>
<p>The specifics of platform enforcement appear in the sections labeled
&quot;runtime requirements&quot; in the <a href="#use-cases">intended use cases and enforcement for each
foreground service type</a> section on this page.</p>

<h2 id="use-cases" data-text="Intended use cases and enforcement for each foreground service type" tabindex="-1">Intended use cases and enforcement for each foreground service type</h2>

requirements, and your app must fulfill one of the intended sets of use cases
for that type. The following sections explain the permission that you must
declare, the runtime prerequisites, and the intended use cases for each type.</p>

<dt>Constant to pass to <code translate="no" dir="ltr">startForeground()</code></dt>
<dd><a href="/reference/android/content/pm/ServiceInfo#FOREGROUND_SERVICE_TYPE_SHORT_SERVICE"><code translate="no" dir="ltr">FOREGROUND_SERVICE_TYPE_SHORT_SERVICE</code></a></dd>
<dt>Runtime prerequisites</dt>
<dd>None</dd>
<dt>Description</dt>
<dd><p>Quickly finish critical work that cannot be interrupted or postponed.</p>

<p>This type has some unique characteristics:</p>

<ul>
<li>Can only run for a short period of time (about 3 minutes).</li>
<li>No support for <a href="/reference/android/app/Service#START_STICKY">sticky</a> foreground services.</li>
<li>Cannot start other foreground services.</li>
<li>Doesn&#39;t require a <a href="#permission-for-fgs-type">type-specific permission</a>, though it still
requires the <a href="/reference/android/Manifest.permission#FOREGROUND_SERVICE"><code translate="no" dir="ltr">FOREGROUND_SERVICE</code></a> permission.</li>
<li>A <code translate="no" dir="ltr">shortService</code> can only change to another service type if the app is
currently eligible to start a new foreground service.</li>
<li>A foreground service can change its type to <code translate="no" dir="ltr">shortService</code> at any time,
at which point the timeout period begins.</li>
</ul>

<p>The timeout for shortService begins from the moment that
<a href="/reference/android/app/Service#startForeground(int,%20android.app.Notification,%20int)"><code translate="no" dir="ltr">Service.startForeground()</code></a> is called. The app is expected to call
<a href="/reference/android/app/Service#stopSelf()"><code translate="no" dir="ltr">Service.stopSelf()</code></a> or <a href="/reference/android/app/Service#stopForeground(int)"><code translate="no" dir="ltr">Service.stopForeground()</code></a> before the
timeout occurs. Otherwise, the new <code translate="no" dir="ltr">Service.onTimeout()</code> is called, giving
apps a brief opportunity to call <code translate="no" dir="ltr">stopSelf()</code> or <code translate="no" dir="ltr">stopForeground()</code> to stop
their service.</p>

<p>A short time after <code translate="no" dir="ltr">Service.onTimeout()</code> is called, the app enters a <a href="/guide/components/activities/process-lifecycle">cached
state</a> and is no longer considered to be in the foreground, unless the
user is actively interacting with the app. A short time after the app is
cached and the service has not stopped, the app receives an <a href="/topic/performance/issues/anr">ANR</a>. The
ANR message mentions <code translate="no" dir="ltr">FOREGROUND_SERVICE_TYPE_SHORT_SERVICE</code>. For these
reasons, it&#39;s considered best practice to implement the
<code translate="no" dir="ltr">Service.onTimeout()</code> callback.</p>

<p>The <code translate="no" dir="ltr">Service.onTimeout()</code> callback doesn&#39;t exist on Android 13 and lower. If
the same service runs on such devices, it doesn&#39;t receive a timeout, nor
does it ANR. Make sure that your service stops as soon as it finishes the
processing task, even if it hasn&#39;t received the <code translate="no" dir="ltr">Service.onTimeout()</code>
callback yet.</p>

<p>It&#39;s important to note that if the timeout of the <code translate="no" dir="ltr">shortService</code> is not
respected, the app will ANR even if it has other valid foreground services
or other app lifecycle processes running.</p>

<p>If an app is visible to the user or satisfies one of the <a href="/guide/components/foreground-services#background-start-restriction-exemptions">exemptions</a>
that allow foreground services to be started from the background, calling
<code translate="no" dir="ltr">Service.StartForeground()</code> again with the
<code translate="no" dir="ltr">FOREGROUND_SERVICE_TYPE_SHORT_SERVICE</code> parameter extends the timeout by
another 3 minutes. If the app isn&#39;t visible to the user and doesn&#39;t
satisfy one of the <a href="/guide/components/foreground-services#background-start-restriction-exemptions">exemptions</a>, any attempt to start another
foreground service, regardless of type, causes a
<a href="/reference/android/app/ForegroundServiceStartNotAllowedException"><code translate="no" dir="ltr">ForegroundServiceStartNotAllowedException</code></a>.</p>

<p>If a user disables <a href="https://support.google.com/pixelphone/answer/7015477" class="external">battery optimization</a> for your app, it&#39;s
still affected by the timeout of shortService FGS.</p>

<p>If you start a foreground service that includes the <code translate="no" dir="ltr">shortService</code> type and
another foreground service type, the system ignores the <code translate="no" dir="ltr">shortService</code> type
declaration. However, the service must still adhere to the prerequisites of
the other declared types. For more information, see the <a href="/guide/components/foreground-services">Foreground services
documentation</a>.</p></dd>
</dl>

<h3 id="special-use" data-text="Special use" tabindex="-1">Special use</h3>


<dl>
<dt>Foreground service type to declare in manifest under</dt>
<dt><code translate="no" dir="ltr">android:foregroundServiceType</code></dt>
<dd><code translate="no" dir="ltr">specialUse</code></dd>
<dt>Permission to declare in your manifest</dt>
<dd><a href="/reference/android/Manifest.permission#FOREGROUND_SERVICE_SPECIAL_USE"><code translate="no" dir="ltr">FOREGROUND_SERVICE_SPECIAL_USE</code></a></dd>
<dt>Constant to pass to <code translate="no" dir="ltr">startForeground()</code></dt>
<dd><a href="/reference/android/content/pm/ServiceInfo#FOREGROUND_SERVICE_TYPE_SPECIAL_USE"><code translate="no" dir="ltr">FOREGROUND_SERVICE_TYPE_SPECIAL_USE</code></a></dd>
<dt>Runtime prerequisites</dt>
<dd>None</dd>
<dt>Description</dt>
<dd><p>Covers any valid foreground service use cases that aren&#39;t covered by the other
foreground service types.</p>

<p>In addition to declaring the <code translate="no" dir="ltr">FOREGROUND_SERVICE_TYPE_SPECIAL_USE</code>
foreground service type, developers should declare use cases in the
manifest. To do so, they specify the <code translate="no" dir="ltr">&lt;property&gt;</code> element within the
<a href="/guide/topics/manifest/service-element"><code translate="no" dir="ltr">&lt;service&gt;</code></a> element. These values and corresponding use cases are
reviewed when you submit your app in the Google Play Console. The use
cases you provide are free-form, and you should make sure to provide enough
information to let the reviewer see why you need to use the <code translate="no" dir="ltr">specialUse</code>
type.</p>
<div></div><devsite-code><pre class="devsite-click-to-copy" translate="no" dir="ltr" is-upgraded syntax="XML"><code translate="no" dir="ltr">&lt;service<span class="devsite-syntax-w"> </span>android:name="fooService"<span class="devsite-syntax-w"> </span>android:foregroundServiceType="specialUse"&gt;
<span class="devsite-syntax-w">  </span>&lt;property<span class="devsite-syntax-w"> </span>android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE"
<span class="devsite-syntax-w">      </span>android:value="explanation_for_special_use"/&gt;
&lt;/service&gt;
</code></pre></devsite-code></dd>
</dl>

<h3 id="system-exempted" data-text="System exempted" tabindex="-1">System exempted</h3>


<dl>
<dt>Foreground service type to declare in manifest under</dt>
<dt><code translate="no" dir="ltr">android:foregroundServiceType</code></dt>
<dd><code translate="no" dir="ltr">systemExempted</code></dd>
<dt>Permission to declare in your manifest</dt>
<dd><a href="/reference/android/Manifest.permission#FOREGROUND_SERVICE_SYSTEM_EXEMPTED"><code translate="no" dir="ltr">FOREGROUND_SERVICE_SYSTEM_EXEMPTED</code></a></dd>
<dt>Constant to pass to <code translate="no" dir="ltr">startForeground()</code></dt>
<dd><a href="/reference/android/content/pm/ServiceInfo#FOREGROUND_SERVICE_TYPE_SYSTEM_EXEMPTED"><code translate="no" dir="ltr">FOREGROUND_SERVICE_TYPE_SYSTEM_EXEMPTED</code></a></dd>
<dt>Runtime prerequisites</dt>
<dd>None</dd>
<dt>Description</dt>
<dd><p>Reserved for system applications and specific system integrations, to
continue to use foreground services.</p>

<p>To use this type, an app must meet at least one of the following criteria:</p></dd>
</dl>

<ul>
<li>Device is in demo mode state</li>
<li>App is a <a href="https://source.android.com/devices/tech/admin/provision" class="external">Device Owner</a> </li>
<li>App is a <a href="https://source.android.com/devices/tech/admin/managed-profiles" class="external">Profiler Owner</a> </li>
<li>Safety Apps that have the <a href="/reference/android/app/role/RoleManager#ROLE_EMERGENCY"><code translate="no" dir="ltr">ROLE_EMERGENCY</code></a> role</li>
<li><a href="/work/device-admin">Device Admin</a> apps</li>
<li>Apps holding <a href="/reference/android/Manifest.permission#SCHEDULE_EXACT_ALARM"><code translate="no" dir="ltr">SCHEDULE_EXACT_ALARM</code></a> or
<a href="/reference/android/Manifest.permission#USE_EXACT_ALARM"><code translate="no" dir="ltr">USE_EXACT_ALARM</code></a> permission and are using
Foreground Service to continue alarms in the background,
including haptics-only alarms.</li>
<li><p>VPN apps (configured using <strong>Settings &gt; Network &amp; Internet &gt; VPN</strong>)</p>

<p>Otherwise, declaring this type causes the system to throw a
<code translate="no" dir="ltr">ForegroundServiceTypeNotAllowedException</code>.</p></li>
</ul>

<h2 id="google-play-enforcement" data-text="Google Play policy enforcement for using foreground service types" tabindex="-1">Google Play policy enforcement for using foreground service types</h2>


<p>If your app targets Android 14 or higher, you&#39;ll need to declare your app&#39;s
foreground service types in the Play Console&#39;s app content page (<strong>Policy &gt;
App content</strong>). For more information on how to declare your foreground
service types in Play Console, see <a href="https://support.google.com/googleplay/android-developer/answer/13392821">Understanding foreground service and
full-screen intent requirements</a>.</p>
