<p>Android 10 includes updated system behavior changes that may affect your app.
The changes listed on this page apply exclusively to apps that are targeting
API 29 or higher. If your app sets <code translate="no" dir="ltr">targetSdkVersion</code> to &quot;29&quot; or
higher, you should modify your app to support these behaviors properly,
where applicable.</p>

<p>Make sure to also review the list of <a href="/about/versions/10/behavior-changes-all">behavior changes that affect all apps
running on Android 10</a>.</p>

<div class="note">
  <p><b>Note: </b>In addition to the changes listed on this page, Android 10
  introduces a large number of privacy-based changes and restrictions, including
  the following:</p>
  <ul>
    <li>Scoped storage</li>
    <li>Access to USB device serial number</li>
    <li>Ability to enable, disable, and configure Wi-Fi</li>
    <li>Location permissions for connectivity APIs</li>
  </ul>
  <p>These changes, which affect apps that target API level 29 or higher,
  enhance user privacy. To learn more about how to support these changes, see
  the <a href="/about/versions/10/privacy/changes">Privacy changes</a> page.</p>
</div>

<h2 id="non-sdk-restrictions" data-text="Updates to non-SDK interface restrictions" tabindex="-1">Updates to non-SDK interface restrictions</h2>

<p>To help ensure app stability and compatibility, the platform started restricting
which <a href="/guide/app-compatibility/restrictions-non-sdk-interfaces">non-SDK interfaces</a>
your app can use in Android 9 (API level 28). Android 10 includes updated lists
of restricted non-SDK interfaces based on collaboration with Android developers
and the latest internal testing. Our goal is to make sure that public
alternatives are available before we restrict non-SDK interfaces.</p>

<p>If you will not be targeting Android 10 (API level 29), some of these changes
might not immediately affect you. However, while you can currently use some
non-SDK interfaces (<a href="/guide/app-compatibility/restrictions-non-sdk-interfaces#list-names">depending on your app&#39;s target API level</a>),
using any non-SDK method or field always carries a high risk of breaking your
app.</p>

<p>If you are unsure if your app uses non-SDK interfaces, you can
<a href="/guide/app-compatibility/restrictions-non-sdk-interfaces#test-for-non-sdk">test your app</a> to
find out. If your app relies on non-SDK interfaces, you should begin planning a
migration to SDK alternatives. Nevertheless, we understand that some apps have
valid use cases for using non-SDK interfaces. If you cannot find an alternative
to using a non-SDK interface for a feature in your app, you should
<a href="/guide/app-compatibility/restrictions-non-sdk-interfaces#feature-request">request a new public API</a>.</p>

<p>To learn more, see <a href="/about/versions/10/non-sdk-q">Updates to non-SDK interface restrictions in Android 10</a>
and see <a href="/guide/app-compatibility/restrictions-non-sdk-interfaces">Restrictions on non-SDK interfaces</a>.</p>

<h2 id="shared-memory" data-text="Shared memory" tabindex="-1">Shared memory</h2>

<p>Ashmem has changed the format of dalvik maps in /proc/&lt;pid&gt;/maps,
affecting apps that directly parse the maps file. Application developers should
test the /proc/&lt;pid&gt;/maps format on devices that run
Android&nbsp;10 or higher and parse accordingly if the app depends on
dalvik map formats.</p>

<p>Apps targeting Android&nbsp;10 cannot directly use ashmem
(/dev/ashmem) and must instead access shared memory via the NDK’s
<a href="https://android.googlesource.com/platform/frameworks/base/+/master/native/android/sharedmem.cpp"><code translate="no" dir="ltr">ASharedMemory</code> class</a>.
In addition, apps cannot make direct IOCTLs to existing ashmem file descriptors
and must instead use either the NDK’s <code translate="no" dir="ltr">ASharedMemory</code> class or the Android Java
APIs for creating shared memory regions. This change increases security and
robustness when working with shared memory, improving performance and security
of Android overall.</p>

<h2 id="execute-permission" data-text="Removed execute permission for app home directory" tabindex="-1">Removed execute permission for app home directory</h2>

<p>Execution of files from the writable app home directory is a
<a href="https://en.wikipedia.org/wiki/W%5EX" class="external">W^X violation</a>.
Apps should load only the binary code that&#39;s embedded within an app&#39;s APK file.</p>

<p>Untrusted apps that target Android&nbsp;10 cannot invoke <code translate="no" dir="ltr">execve()</code>
directly on files within the app&#39;s home directory.</p>

<p>In addition, apps that target Android&nbsp;10 cannot in-memory modify
executable code from files which have been opened with <code translate="no" dir="ltr">dlopen()</code> and expect
those changes to be written through to disk, because the library cannot have
been mapped <code translate="no" dir="ltr">PROT_EXEC</code> through a writable file descriptor. This includes any
shared object (<code translate="no" dir="ltr">.so</code>) files with text relocations.</p>

<h2 id="system-only-oat" data-text="Android runtime only accepts system-generated OAT files" tabindex="-1">Android runtime only accepts system-generated OAT files</h2>

<p>The Android runtime (ART) no longer invokes <code translate="no" dir="ltr">dex2oat</code> from the application
process. This change means that the ART will only accept OAT files that the
system has generated.</p>

<h2 id="aot" data-text="Enforcing AOT correctness in ART" tabindex="-1">Enforcing AOT correctness in ART</h2>

<p>In the past, the ahead-of-time (AOT) compilation performed by the Android
Runtime (ART) could cause runtime crashes if the classpath environment was not
the same at compile time and runtime. Android&nbsp;10 and higher
always require these environment contexts to be the same, resulting in the
following changes in behavior:</p>

<ul>
<li>Custom class loaders—that is, class loaders written by apps, unlike class
loaders from the <code translate="no" dir="ltr">dalvik.system</code> package—aren&#39;t AOT-compiled. This is because
ART cannot know about customized class lookup implementation at runtime.</li>
<li>Secondary dex files—that is, the dex files loaded manually by apps not in the
primary APK—are AOT-compiled in the background. This is because first-use
compilation might be too expensive, leading to unwanted latency before
execution. Note that for apps, adopting splits and moving away from secondary
dex files is recommended.</li>
<li>Shared libraries in Android (the entries &lt;library&gt; and
&lt;uses-library&gt; in an Android manifest) are implemented using a different
class loader hierarchy than the one used in previous versions of the platform.</li>
</ul>

<h2 id="full-screen-intents" data-text="Permissions changes for fullscreen intents" tabindex="-1">Permissions changes for fullscreen intents</h2>

<p>Apps that target Android&nbsp;10 or higher and use notifications with
<a href="/training/notify-user/build-notification#urgent-message">fullscreen
intents</a> must request
the
<a href="/reference/android/Manifest.permission#USE_FULL_SCREEN_INTENT"><code translate="no" dir="ltr">USE_FULL_SCREEN_INTENT</code></a>
permission in their app&#39;s manifest file. This is a <a href="/guide/topics/permissions/normal-permissions">normal
permission</a>, so the system
automatically grants it to the requesting app.</p>

<p>If an app that targets Android&nbsp;10 or higher attempts to create a
notification with a fullscreen intent without requesting the necessary
permission, the system ignores the fullscreen intent and outputs the following
log message:</p>

<div></div><devsite-code><pre class="none" translate="no" dir="ltr" is-upgraded>
Package <var translate="no">your-package-name</var>: Use of fullScreenIntent requires the USE_FULL_SCREEN_INTENT permission
</pre></devsite-code>

<h2 id="foldables" data-text="Support for foldables" tabindex="-1">Support for foldables</h2>

<p>Android&nbsp;10 has changes that support foldables and large screen devices.</p>

<p>When an app runs on Android&nbsp;10, the
<a href="/reference/android/app/Activity#onResume()"><code translate="no" dir="ltr">onResume()</code></a> and
<a href="/reference/android/app/Activity#onPause()"><code translate="no" dir="ltr">onPause()</code></a> methods work
differently. When multiple apps appear at the same time in multi-window or
multi-display mode, all the focusable top activities in visible stacks
are in the resumed state, but only one of them, the &quot;topmost resumed&quot; activity,
actually has focus. When running on versions earlier than Android&nbsp;10, only a
single activity in the system can be resumed at a time, all other visible
activities are paused.</p>

<p>Do not confuse &quot;focus&quot; with the &quot;topmost resumed&quot; activity. The system assigns
priorities to activities based on  z-order to give higher priority to
the activities that the user interacted with last. An activity can be
top-resumed, but not have focus (for example, if the notification shade is
expanded).</p>

<p>In Android&nbsp;10 (API level 29) and later, you can subscribe to the
<a href="/reference/android/app/Activity#onTopResumedActivityChanged(boolean)"><code translate="no" dir="ltr">onTopResumedActivityChanged()</code></a> callback
to be notified when your activity acquires or loses the topmost resumed
position. This is the equivalent of the resumed state before Android&nbsp;10 and can be useful
as a hint if your app is using exclusive or singleton resources that might need
to be shared with other apps.</p>

<p>The behavior of the
<a href="/guide/topics/ui/multi-window#resizeableActivity"><code translate="no" dir="ltr">resizeableActivity</code></a>
manifest attribute has also changed. If an app sets
<code translate="no" dir="ltr">resizeableActivity=false</code> in Android&nbsp;10 (API level 29) or later, it might be put in compatibility mode
when the available screen size changes, or if the app moves from one screen to
another.</p>

<p>Apps can use the
<a href="/reference/android/R.attr#minAspectRatio"><code translate="no" dir="ltr">android:minAspectRatio</code></a>
attribute, introduced in Android&nbsp;10, to indicate the <a href="/guide/topics/ui/foldables#new_screen_ratios">screen
ratios</a> that your app supports.</p>

<p>Starting with version 3.5, Android Studio&#39;s emulator tool
includes 7.3&quot; and 8&quot; virtual devices for testing your code with larger screens.</p>
